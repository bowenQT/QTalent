功能模块规划

按侧栏的「人 / 项目 / 规则」分组，加上入口和平台两组。比赛一栏分开写原型和验证工程；上面选中的阶段在这里高亮。

一条证据链，三条主线

项目找人读已确认的证据，重点跟踪读已确认的事件，盘点读已确认的分和冻结快照。实线框是比赛验证工程要真实跑通的环节，虚线框留在原型演示。

权限、北森同步与系统管理

这三块是平台能力，不新增业务领域：同步来的事实归人员与组织、材料与记录两个领域，授权仍由人员与组织领域维护；同步任务、集成配置和审计在平台层。

角色是权限预设

每次读取都按这四项判断

当前账号×动作×范围×用途
预设能做什么范围
管理者看人与档案、找人、确认规则修订和找人方案；读 HR 的复核、方案与复盘全公司
HR记录、整理档案、评分复核、象限校准、留用与落位方案、节点复盘、规则起草、判断对照归因、标签库按学员名单与有效期
导师记录所带学员、确认本人评分、对人复盘、提修订建议、我的判断对照；看不到象限所带学员
系统管理员账号、角色与范围、北森同步、集成配置、审计日志系统配置；看不到人才数据
CEO 长期管理者细分；规则修订与找人方案的确认权先只给 CEO全公司
部门负责人 长期管理者细分；项目 owner 身份不扩大团队名单本组织子树
员工本人 长期本人的经历、已发布的反馈与行动、自述与发展意愿；看不到维度分、象限、被关注与被推荐本人
HR 授权口径

HR 按学员名单看这个人的全部资料

包括学员进入下一期、留用进部门之后的资料。执行时有三条：

  1. 名单带有效期，各有唯一维护方：「HR 负责哪些期次」由系统管理员配置，「期次里有哪些学员」由 HR 在人才项目里维护；不再负责这一期，访问随之结束。名单就是授权，增补只能加北森在职人员，开营时整份名单和之后的逐人增补都要管理者确认，确认前只看本期资料。
  2. 多重身份取完整授权的并集：同时是导师和评价人、或同时负责两个期次时，按各身份各自的「动作 + 范围」合并，不把一个身份的动作和另一个身份的范围拼在一起。
  3. 访问留审计：档案、原件、绩效这类敏感读取都记访问日志，系统管理员和 HR 负责人可查。
系统管理员与数据访问分开

管理员能配置谁看什么，自己默认什么人才数据都看不到。管理员账号不持有业务预设；授予或扩大管理者、HR 预设和 HR 负责的期次，由管理员发起、管理者确认后生效。每次授权变更都留审计，排查问题只看任务状态、错误类型和同步记录。

北森同步 · 中期上线

北森是组织、人员与人事数据的主数据源，只读同步，不回写

北森开放接口只读凭证只在服务端；只申请下表里的字段
北森适配器定时增量拉取，定期全量对账；每次同步留批次记录
暂存与校验字段白名单、人员编号对照、冲突检查；校验通过后按实体在事务里写入
组织、人员、任职、职级、入离调转 → 人员与组织 绩效、晋升（原口径历史事实）→ 材料与记录 接口失败、映射缺失 → 系统管理员处理 匹配不到、疑似同一人、任职重叠 → HR 负责人确认，确认前隔离 离职、调岗 → 撤销或调整账号与范围
数据用法与边界
组织架构部门负责人的「组织子树」范围和团队分布都按它算
人员与任职按需求定稿的字段白名单取；健康、家庭、联系方式等不同步
入离调转离职当天停用账号并收回范围；调岗按新组织重算范围
职级档案里展示当前职级与变化
绩效结果、晋升记录单独的来源类型「北森人事记录」，用途只有档案展示：只给管理者和 HR 看，按原口径展示；不换算成维度分，不进象限、值得关注、判断对照和找人证据，不进入任何模型输入，不排序

冲突时组织、人员、任职以北森为准；人才项目名单、导师关系、评价与校准是 Niu-Talent 自己的事实，北森同步不覆盖。人才项目、期次、学员名单、导师分配是 HR 的业务操作，归人才项目领域，不放进系统管理。

比赛链路与八条合同

执行顺序 P0 → P1 → P2 → P3 → P5 → P4，六条全部必做。实时推流建在完整归档和离线稿之上，实时稿只做预览；时间不够时先压缩各条链路内部的范围。

  1. 做什么演示要证明的事依赖
  2. P0
    骨架与权限三个预置账号登录、范围过滤、PostgreSQL、第六期演示数据导入，工作台与档案读真实库
    权限在服务端生效—
  3. P1
    记一件事一句话 → MaaS 整理 SBI 和建议分 → 服务端校验引用与锚点 → 导师确认或改分 → 分差大的进 HR 复核 → 档案更新
    AI 只给建议，人确认才生效，引用可回查P0
  4. P2
    找人（含 Jev）需求卡逐条匹配已确认证据 → Jev 判四态 → 每条回到来源；Jev 出错只改处理进度，显示「待人工判断」
    找人只用四种状态、不出总分，判断能追溯P0；可用 P1 的事件
  5. P3
    离线转写上传录音 → Kodo → 听悟离线 → 说话人与人员绑定 → 走 P1 的整理，引用到时间点
    录音进入同一条证据链P0、P1
  6. P5
    实时推流桌面浏览器 → WebSocket → 常驻后台 → 听悟实时预览；断线重连、暂停续录，结束后以离线稿为准
    现场录音的实时体验P3；常驻进程
  7. P4
    文本附件TXT、DOCX、文字型 PDF → 段落 → 走 P1，引用到页和段
    文件进入同一条证据链P0、P1
比赛必须守住的八条合同

守住这些，中期复用还是重建都不返工

  1. 来源链：引用存来源片段 ID、原件版本和位置
  2. 建议与确认分开：确认后才进档案和象限；分差 2 分以上进 HR 复核
  3. 服务端先过滤：接口响应和模型输入都按范围构造
  4. 结论与处理进度分开：四态是结论；排队、判断中、待人工判断、失败是进度
  5. 录音以归档为准：音频先完整存入 Kodo，离线稿是事件提取的唯一来源
  6. 不出现总分、排名、百分比；Jev confidence 不出前端
  7. 确认只生效一次：请求重放、业务唯一键、修订冲突三层
  8. 版本标记：事件保存时记录生效的锚点版本，之后不静默重算
留在原型演示

主要是库内规则与事务，技术不确定性低

  • 判断对照、节点复盘与改进事项
  • 人才评价规则的修订、预览与发布
  • 盘点、象限校准与冻结、留用与落位
  • 值得关注、我的关注、推荐方向
  • 系统管理员与北森同步（演示视角）

验证工程的时间优先花在外部服务和证据链这些不确定的地方。手机端的锁屏、切页、长录音这次验证不了，演示时照实说明。

三个阶段始终不做

这些是产品不变量，任何实现细节都不能绕过。

  • 综合人才总分、能力百分比、全公司排名、按分数排序的人员列表
  • 雷达图、没有标准的九宫格；能力象限只用 2×2
  • AI 建议分未经人确认就计入档案和象限
  • 把北森绩效、晋升换算成维度分、象限或任何综合分
  • 向北森回写数据
  • 把「资料不足」当作反向证据或低潜力
  • 把 Jev confidence 显示为能力分或胜任率
  • 静默重算历史分数、冻结快照和档案版本
  • 由系统自动做人事决定
