# 界面文案规范

本规范约束 Niu-Talent 所有面向用户的界面文案，适用于原型（`prototype/app/`、`prototype/m/`）、设计系统样张、共用模块拼出的字符串，以及正式开发阶段的界面。写法参照 Apple Human Interface Guidelines（Writing）、Google Material Design（Content design）、Microsoft Writing Style Guide 的公开原则，以及小米等一流产品的中文界面写法：直接、具体、口语、以用户任务为中心。

产品不变量见 [AGENTS.md](../AGENTS.md#产品不变量)。本规范只管「怎么写」，不改变不变量本身；文案改写必须保持原有事实、权限范围和不变量。需求定稿里指定的文案与本规范冲突时，按权威顺序处理，并把冲突记进下一版需求修订。

## 适用范围

| 硬约束（四类禁止写法必须遵守） | 建议遵守 | 不纳入 |
| --- | --- | --- |
| 标题、按钮、菜单、标签页、表头、筛选项 | `design-system.html` 里写给设计和开发看的用法说明，为讲清规则可以用否定句 | 代码注释、变量名 |
| 提示、空状态、加载与处理中、成功与失败、确认弹窗、toast | 评审导览 `prototype/index.html` 的叙事说明 | 演示人员录入的原话、转写、引用原文（属于证据，保持原样） |
| 表单标签、占位符（含示例句）、校验提示 | | 需求编号、AC 编号（只出现在注释与文档里） |
| AI 以产品口吻输出的摘要、建议、归因假设、追问回答 | | |
| mock 数据里由产品撰写的字段：标签定义、行为锚点、规则说明、任务说明、状态文字 | | |
| IP 形象的状态名与台词；设计系统样张里会上界面的文字 | | |

## 写法总则

1. **说现在是什么、接下来做什么。** 每段文案只回答用户此刻最关心的一件事：状态、结果或下一步。
2. **一句一意，短句优先。** 按钮 2–6 字，标题不超过 12 字，提示一句话说完，不超过一行半。
3. **主操作写动作和对象。** 「确认分数」「改为归档」「请 HRBP 复核」。避免「确定」「提交」「OK」这类不说结果的词；弹窗标题已写明对象时，主按钮可以只写动作（「添加成员到……」配「添加」）。
4. **用用户的词。** 用业务里的人、事、物：人、事件、证据、档案、盘点、方案。内部名称不上界面，见 [内部名称](#内部名称)。
5. **同一个东西只有一个名字。** 术语以 [受控术语](#受控术语) 和需求定稿为准，全站一致。
6. **规则靠结构表达，不靠句子声明。** 权限、可见范围、AI 与人工的区分，用界面结构、徽标、分区和入口体现。只有用户在当下要据此做决定时，才在决策点用一句肯定句说明。

## 四类禁止写法

### 1. 否定句式

用肯定句写事实、状态和下一步。否定句让用户先想「不是什么」，再自己推出「是什么」。

- **识别信号**：`不`、`没`、`没有`、`无`、`无法`、`不能`、`不会`、`未`、`尚未`、`别`、`勿`、`非`、`暂无`、`不再`。
- **例外**：[受控术语](#受控术语) 作为状态名或标签原样使用；证据原文保持原样。
- **改法**：
  - 空状态写「这里会出现什么」或「已经完成了什么」，可以带上怎么开始。
  - 缺失写「待 + 动作」：待补充、待校准、待沟通。
  - 限制写「能做什么、在哪里做」。
  - 权限写「谁能看到」，用「仅」「只」限定范围，名单必须与真实权限一致。
  - 失败写「发生了什么 + 怎么办」。

| 原文 | 改为 |
| --- | --- |
| 暂时没有要你决定的事。 | 需要你决定的事都处理完了 |
| 还没有已确认的关键事件。 | 确认后的关键事件会出现在这里 |
| 一次最多 5 个文件，多出的 2 个没有加入 | 已加入前 5 个文件，其余 2 个请再选一次 |
| 员工视角不录音。可以在「档案」里补充自己的经历。 | 在「档案」里补充你的经历（同时隐藏录音入口） |
| 依据已经变化，这条假设不能按原文确认 | 依据已更新，请按新依据重新确认 |
| 你看不到其他评价人的判断 | 这里只显示你本人的判断 |
| 原话没写影响，可以补上 | 补充影响 |
| 上传完成前别关页面 | 上传时请保持页面打开 |

### 2. 欧化句式

按中文的语序和节奏写，少用翻译腔。

| 信号 | 例 | 改法 |
| --- | --- | --- |
| 「被」字被动 | 该线索已被 HRBP 核实 | HRBP 已核实这条线索；口语里表达不如意的「被」（方案被否、被问住）是自然中文，可以保留 |
| 「进行 / 作出 / 加以」+ 动词 | 进行校准、作出确认 | 校准、确认 |
| 「对于 / 关于 / 基于 / 针对……」开头 | 基于已确认的证据，系统…… | 按已确认的证据…… |
| 「当……时」「在……的情况下」 | 当录音中断时 | 录音中断后 |
| 「通过……来」「使得」「从而」 | 通过关注来追踪 | 关注后可以随时看到进展 |
| 「作为」「具有」「存在」做谓语 | 具有潜力、存在冲突 | 有潜力、证据冲突 |
| 「以……的身份」「对……的」 | 以苏晚的身份查看 | 当前视角：苏晚 |
| 「将」表将来 | 确认后将生成行动 | 确认后生成行动 |
| 长定语、连续「的」 | 已确认的事件的维度分的变化 | 已确认事件的分数变化 |
| 名词化堆叠 | 完成对假设的确认 | 确认假设 |
| 多余的量词与代词 | 一个新的版本、你的档案 | 新版本、档案 |
| 英文句读 | 半角逗号句号、英文引号 | 中文全角标点，界面元素名用「」 |

### 3.「不是 X，而是 Y」对举

这类句式先立一个用户没提的错误认识再纠正，读起来像辩解。同类：`不是……而是……`、`不是……是……`、`……，而不是……`、`……而非……`、`与其……不如……`、`不在于……而在于……`、`并非……`、`不止……`。

- **改法**：只写 Y。行为锚点、标签定义同样适用。

| 原文 | 改为 |
| --- | --- |
| 复盘的对象是判断，不是被评价的人 | 复盘对照的是判断：同一个人、同一维度，前后两段评价放在一起看 |
| 跟踪不是收藏：要写清为什么关注…… | 写清为什么关注、想观察什么、谁负责、下次什么时候看 |
| 从客户实际的使用场景出发重新理解需求，而不是只照着需求文档执行 | 从客户实际的使用场景出发，重新理解需求 |

### 4. 免责声明与过程解释

界面不替系统辩护，也不讲 Agent 正在怎么做。

**免责声明**：`仅供参考`、`不代表……`、`不等于……`、`不构成……`、`不当作……`、`不改变……`、`AI 可能出错`、`以实际为准`，以及一串「只统计……不算……不按……」的规则说明。

- 规则由产品行为保证：AI 建议用「AI 建议」徽标和独立分区呈现，未确认的分数不进入档案，权限外的内容和入口直接隐藏。
- 用户在当下需要据此判断时，在决策点写一句肯定句，例如校准弹窗写「确认后计入档案」，方案确认弹窗写「确认后冻结快照并生成跟进行动」。
- 完整规则放进评价体系页、帮助或速览里的「依据」，按需展开。

**过程解释**：`AI 正在为你……`、`我将……`、`系统会先……然后……`、`AI 拿不准……`、`正在调用……`、算法与取数规则的说明，以及 `原型不读取真实文件`、`占位值，联调后填写` 这类研发说明。

- 进行中只写状态和进度：「整理中」「转写中 3/12」，过程由 IP 形象的动效表达。
- **进度轨迹**（需求 v1.2「过程可见，但不打扰」）保留：标题写「动作 + 对象 · N 步」，每一步是 2–8 字的动宾短语（「识别人员与项目」「整理关键事件」），默认可折叠。步骤里不写原因、条件和叙述句。
- 完成后直接给结果，不复述做了哪些步骤。
- 原型的演示限制统一用「演示」徽标或评审导览说明，不写进界面句子。

| 原文 | 改为 |
| --- | --- |
| 只统计已确认的事件和分数，AI 建议分不会触发变化。资料从无到有不算上升；没有新事件不等于能力下降。变化按发生时间排列，不按幅度给人排名。 | 按时间列出已确认的变化 |
| 差异需要复核，不代表员工退步，也不直接认定标准或评价人有错。 | 这处差异待复核 |
| 请保持亮屏：锁屏或切到后台会暂停录音，已录的分段已上传，回来可以接着录。 | 录音时保持亮屏。切到后台会暂停，回来接着录，已录内容都已保存。 |
| 录音和文档里有几处 AI 拿不准是谁、是哪个项目。选一下就生效。 | 选出这几处说的是谁、哪个项目，选完即生效 |
| 正在播放这一段录音（原型不含真实音频） | 播放中（配「演示」徽标） |

## 改写守则

改掉违规句式时，同时守住下面几条，避免改出新问题：

- **换皮否定也算否定。** 「暂无」「尚未」「未能」「无法」只是换了字，改成肯定句或「待 + 动作」。
- **不写公文腔。** 少用「予以」「妥善」「均」「该」「此」「开展」「相关」「仅限……开放」「支持（某能力）」。界面是对人说话，用口语短句。
- **事实不增不减。** 改写不能新增原文没有的判断（如「表现稳定」）、功能承诺或流程；不能改变权限名单，「仅 HRBP 和评价人本人可见」必须与真实权限一致。
- **守住不变量。** 改写不能暗示排序、分数或准确率，例如「按匹配度排列」；资料不足的说法只指向「补充材料」，不写成低于某个标准。
- **能删就删。** 删掉后用户没有少知道任何需要的东西，就删整句，不改写。

## 受控术语

以下状态名由需求定稿与产品不变量规定，作为标签、状态、分区名原样使用，不算否定句。它们只做名词性标签，不扩写成否定谓语，例如「资料不足不作为反向证据」仍属违规。

| 术语 | 含义 | 用法 |
| --- | --- | --- |
| 支持 / 不支持 / 资料不足 / 证据冲突 | 项目要求匹配的四种状态 | 只用这四个，不加程度词；「不支持」只指匹配状态，文件格式等错误另写 |
| 资料不足 | 证据不够落位或出分 | 分区名与状态；配下一步「补充材料」 |
| 未体现 | 某维度在该事件里没有出现 | 维度状态，不出分 |
| 样本不足 | 判断复盘可对照案例未到门槛 | 替代任何数字结论 |
| 不可比 | 前后两段情境不同，无法对照 | 复盘案例状态 |
| 不采纳 | 线索的处理结果 | 线索状态与按钮，要求填理由 |
| 未知 | 意愿、释放等信息缺失 | 状态值，不写成 0 |
| 未执行 | 行动没有按计划执行（PRD 行动状态） | 状态值，配一句原因，不写成员工的失败 |
| 暂无 | 「值得关注」分类计数为零（需求 v1.4） | 只做计数位的占位，不进句子 |
| 演示 | 化名与演示数据 | 徽标 |

新增带否定字样的术语前，先找肯定式名称；确需保留的，补进本表并在需求定稿中写明。

## 内部名称

以下内容不上界面，评价体系页、规则版本历史等用户要据此做判断的页面除外：

- 规则与版本代号：`rubric-v1`、`change-v1`、`watch-v2`、`规则 T2`、对应表编号。普通页面写「当前评价规则」或直接省略。
- 模型与引擎名：`qwen-max` 等，界面统一称「AI」。`Jev` 是否作为对外名称尚未在需求中确定，确定前按内部名处理。
- 需求编号与版本：`v1.5`、`3.34`、`AC-57`。
- 技术实现：服务端、接口、存储、预置、占位、联调。

## 分场景写法

| 场景 | 写法 | 例 |
| --- | --- | --- |
| 页面与卡片标题 | 名词短语，说这里是什么 | 值得关注、判断复盘 |
| 主按钮 | 动词 + 对象；标题已写明对象时可只写动作 | 确认分数、补充材料、改为归档 |
| 单按钮告知弹窗 | 「知道了」 | 知道了 |
| 关闭类按钮 | 统一用「取消」；禁止「不取消」「再看看」「不要」「算了」。两个按钮都会带「取消」时，关闭按钮改写成保留什么 | 取消 / 改为归档；保留推动 / 取消推动 |
| 二选一的去留 | 写清去向 | 加入复盘，逐项确认 / 删掉这条；收录 / 并入 / 忽略 |
| 展开与折叠 | 统一「展开 / 收起」；「查看」只用于跳转 | 展开已处理 |
| 跳转链接 | 「查看 + 对象」或「全部 + 对象」 | 查看全部复盘 |
| 空状态 | 这里会出现什么 + 怎么开始 | 记下的事件会出现在这里。按住说话开始记录 |
| 全部处理完 | 写完成了什么 | 需要你决定的事都处理完了 |
| 筛选或搜索结果为空 | 直接给下一步 | 换个筛选条件试试；按回车，把「……」交给 AI 记录 |
| 链接打不开 | 对象 + 链接失效，正文给出路 | 项目链接失效 / 可能已删除，或链接有误。回到项目列表重新进入 |
| 加载 / 处理中 | 名词 + 中，有总量时带进度 | 转写中 3/12 |
| 成功 toast | 结果 + 去向，需要时带「撤销」 | 已核实，唐果会出现在 CEO 的「值得关注」 |
| 撤销 toast | 已撤销 + 对象 | 已撤销这条记录 |
| 已提交但未完成 | 写清当前所处环节 | 已提交，等 HRBP 复核 |
| 失败 | 发生了什么 + 怎么办 | 文件超过 2 GB，剪成几段再传 |
| 确认弹窗 | 标题问动作，正文写后果，主按钮写动作 | 确认这版方案？ / 确认后冻结快照并生成跟进行动 / 取消、确认方案 |
| 权限范围 | 能确认名单时写谁能看到；看不到的整块隐藏 | 仅 HRBP 和评价人本人可见 |
| 部分内容被权限过滤 | 写「已隐藏」，不靠推断列名单 | 另有 3 条动作涉及你范围以外的人，已隐藏；导师视角已隐藏象限 |
| 无权限页面 | 标题写这一页属于其他视角或在查看范围之外，正文给出路 | 这一页属于其他视角 / 切换演示视角，或回到工作台；这个人在你的查看范围之外 |
| AI 内容 | 徽标区分来源，正文直接写建议 | 「AI 建议」4 分 · 依据 2 条 |
| 计数 | 数字 + 量词 + 对象 | 3 人待校准 |
| 占位符 | 示例句也遵守四类禁令 | 比如：演示环境是我和陈一禾一起搭的 |

## 格式

- 中文全角标点；中文与英文、数字之间加半角空格：「AI 建议」「3 人」。
- 界面元素名、受控术语引用用「」。
- 称呼用户用「你」，全站一致。
- 按钮、标签、标题不加句号；完整句子的提示加句号，单句 toast 可省略。
- 数字用阿拉伯数字，日期写「11 月 1 日」「10:30」。

## 自查

提交前对改动涉及的文案逐条过一遍：

- [ ] 这句话去掉后，用户会少知道什么？答不上来就删。
- [ ] 有否定字样吗？受控术语以外的，改成肯定句。
- [ ] 有「不是……而是」「而非」「不止」吗？只留后半句。
- [ ] 有「被」「进行」「对于」「基于」「当……时」「将」吗？换成中文语序。
- [ ] 在替系统解释规则、说明自己怎么做，或露出内部名称吗？交给结构、徽标或帮助。
- [ ] 改写后事实、权限名单和不变量还准确吗？
- [ ] 主按钮写了动作和对象吗？术语和全站一致吗？
