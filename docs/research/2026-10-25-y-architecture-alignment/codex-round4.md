v2 可作为待决策 Draft 交给用户，但不宜直接作为实施依据；最大阻断是授权范围的变更权尚未闭合，存在绕过“不得自授”的设计风险。

1. **阻断｜§3.2、§4.3：名单维护可能成为自行扩权入口。**  
   §4.3一处让管理员配置“HR 的期次与名单”，末段又让 HR 维护学员名单；§3.2则直接由名单授予全部资料读权。若 HR 把其他部门人员加入自己负责的期次，就可能获得其完整档案；管理员互授业务角色也不受“不能给自己授权”限制。  
   **依据**：上述两处写入责任及 v21 §5（v21 研究工作区 `docs/proposals/2026-10-23-application-architecture.md:196`） 的动作与范围绑定原则。**建议**：明确业务名单与授权关系的唯一维护方、可添加人员的边界，以及管理员取得业务权限的独立确认机制；审计不能替代这些限制。**推断，置信度 0.96。**

2. **重要｜§6.5：Cloudflare 准入未覆盖 VPS 直连入口。**  
   稿件只有代理域名与 Access，没有源站访问约束。若 Caddy 或后台端口直接暴露，拿到演示账号的人可通过 VPS 地址及对应 Host 绕过邮箱准入；应用登录仍存在，但“只放 `@qiniu.com`”不成立。  
   **依据**：部署图、入口配置及 [Cloudflare 源站保护说明](https://developers.cloudflare.com/fundamentals/security/protect-your-origin-server/)。**建议**：限制源站入口，并验证本应用的 Access 令牌，覆盖 HTTP 与 WebSocket 握手；验收直接访问源站被拒绝。**推断，置信度 0.98。**

3. **重要｜§4.2、§4.3：北森历史评价缺少明确的用途隔离。**  
   禁用列表写了评分、象限、值得关注和判断对照，却漏了找人及模型提取入口。若复用已有“历史评价”查询，HR 有权读取的绩效等级可能成为 Jev 的匹配依据，超出 U-9 的档案展示口径。  
   **依据**：§4.3绩效行、U-9；[v1.2 §3.9.2](../../../docs/requirements/需求定稿-v1.2.md#L284) 中其他历史评价原本允许进入提取链。**建议**：给北森绩效、晋升独立来源类型和用途白名单，明确只读展示，并从不允许的查询、模型输入中排除。**推断，置信度 0.94。**

4. **重要｜§4.3：同步异常全部交给管理员，缺少业务判定出口。**  
   “人员匹配不到、任职重叠”不全是技术故障。仅看编号和字段名，无法判断旧档案应归谁、哪段任职有效；猜测合并可能把历史评价及访问权归给错误人员，不处理则持续阻塞同步。  
   **依据**：§4.3“异常”；v21 §6.2.4区分技术排障与有权业务人员核对。**建议**：管理员处理重试、映射格式等技术问题；身份与任职歧义交授权 HR 或北森负责人确认，确认前隔离相关实体。**推断，置信度 0.93。**

5. **重要｜§4.4、§6.3：真实功能承诺超过链路验收范围。**  
   矩阵把“方案确认、会议纪要”随整行标为真实可用，P2却只验收逐条匹配与引用，P3/P5只覆盖转写、归档和进入 SBI。按链路交付会缺功能，按矩阵交付则增加工作；方案确认还涉及 v21 §6.5 的成员、快照和行动事务。  
   **建议**：拆开标注这些子功能，统一纳入范围与验收标准，不能用“匹配跑通”代表“方案确认完成”。**依据**：矩阵对应两行与P2/P3/P5内容。**置信度 0.99。**

应保留的两点：

- U-11 的广泛读权本身不与服务端鉴权冲突；到期撤权、完整授权并集，以及接口、导出和模型输入统一检查应保留。
- 北森只读同步、组织任职以北森为准、自有评价不被覆盖，以及绩效不换算为能力分的边界是正确的。
