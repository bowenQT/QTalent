# Issue、Proposal、Commit 与 PR 规范调研

调研日期：2026-10-23，Asia/Singapore。项目：Niu-Talent。

## 结论与当前事实

调研开始时，本项目只有通用的提交、审查、验证及多 Agent 协作原则，没有 `.github/` 模板、贡献指南或完整的事项与提案流程；`git remote -v` 为空。基线提交为 `9a4c2e9`。当前仍在设计系统和独立 HTML 原型阶段，正式工程尚未建立。

适合本项目的方案是：**按需使用 issue 和 proposal，所有远端代码交付经 PR，主线保留简洁的 commit 历史。** 小改动可以直接 PR；需要持续跟踪的工作建 issue；涉及实质取舍才写 proposal。无需每个任务填写四份相同内容。

协作流程现集中维护在 [CONTRIBUTING.md](../../CONTRIBUTING.md)，由 [AGENTS.md](../../AGENTS.md#按需读取) 按任务指引读取，配套两种 issue 表单、proposal 模板和 PR 模板。本文只保存来源与取舍，不是另一份执行规则。用户补充要求的 commit 规范也包含在内。

当前可用的是本地提交格式和文档模板；GitHub 模板展示、标签、合并方式、规则集及 CI 仍待建远端时启用。以 GitHub 为准备目标是本轮工作假设，不代表已决定仓库归属、可见性、套餐或创建权限。建远端与进入第 3 阶段是不同动作，不提前固定正式应用架构、目录、包管理器或测试工具。

## 社区一手实践

| 来源 | 本轮核实到的实践 | 本项目的处理 |
| --- | --- | --- |
| [Vite 缺陷表单](https://github.com/vitejs/vite/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml) | 问题描述、最小复现、环境和补充日志分开收集 | 保留复现与证据；内部项目允许偶发问题记录已知条件，不照搬必须公开复现仓库、固定包管理器字段或缺复现自动关闭 |
| [React RFC 流程](https://github.com/reactjs/rfcs/blob/main/README.md) | 常规改进走 PR，重大变化才走 RFC；接受方案不等于安排实施 | proposal 只覆盖实质取舍，不让小修复排队等方案审批；不复制大型社区的固定公示期 |
| [Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/main/0000-template.md) | 说明动机、替代方案、缺点与未决问题 | 精简为问题、候选与推荐、影响与验证、决议四部分；保留反对理由，不照搬语言设计的完整章节 |
| [Google：小而完整的变更](https://google.github.io/eng-practices/review/developer/small-cls.html) | 范围应围绕完整想法，相关测试随实现；小变更便于审查 | 一个 PR 一个完整目的，不制定通用行数门槛，不把必要验证拆走 |
| [Google：审查标准](https://google.github.io/eng-practices/review/reviewer/standard.html) | 事实和工程依据优于偏好，非关键打磨应标为非阻塞 | 按根因、影响和证据审查；满足目标后收敛，避免反复为风格改写 |
| [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) | type + 可选 scope + 描述；支持破坏性变更说明 | 用英文 type、可选 scope、中文结果描述；不将语法约定扩大成自动发版、固定目录或必须安装 commitlint |

这些实践提供取舍依据，不存在适用于所有团队的“唯一最佳流程”。本项目的判断标准是三天 Hackathon、一人加 AI 的当前协作方式、未来可以增加维护者，以及人事数据与权限需要可靠边界。若以后出现多人持续并行、频繁发布或审查排队，再依据实际问题增加流程。

## GitHub 平台约束的官方复核

- [Issue 与 PR 模板](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates)：模板需要存在于默认分支才能供协作者使用。文件在本地并不代表远端页面已经生效。
- [Issue Forms 语法](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)：表单用 YAML 定义；自定义标签要先在仓库存在，issue type 是组织级设置。因此本轮表单不写死标签、组织类型、账号或看板，只要求必要字段。
- [Issue 自动关闭](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)：closing keywords 的作用与默认分支有关。项目用 `Refs` 处理部分交付及待部署验收，避免代码合入就误关整个任务。
- [审查批准限制](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)：作者不能批准自己的 PR，AI review 也不能代替需要的人类批准。因此单维护者不能直接套用“两人批准”规则；当前按 PR、自查与人的责任执行，新增维护者后启用非作者批准。
- [Squash 合并](https://docs.github.com/en/pull-requests/reference/pull-request-merges)与[提交消息设置](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests)：squash 将一个 PR 汇成主线上的一条提交，默认消息可配置。本项目据此统一 PR 标题与最终 commit，合入后从最新主线开始下一任务。
- [规则集可用性](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)与[可配置规则](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)：可控制 PR、审查、检查、强推等；私有仓库的可用功能受套餐影响。建仓时需回读真实权限和套餐，不能用模板或文字宣称平台已强制。

社区文件与文档链接在本轮读取成功，但其分支内容和平台功能以后可能变化；实际启用前应重新核对。没有据此查询、购买或更改用户的 GitHub 套餐。

## 为什么这样组合

| 决策 | 采用理由 | 代价与重新评估条件 |
| --- | --- | --- |
| 精简入口，各主题各有一个维护源 | AGENTS 保留阶段与关键约束；工程细则在工程规范、协作流程在贡献指南，按任务读取 | 文档移动时需同步路由、链接和模板；不能通过全量导入把上下文负担重新带回入口 |
| 两种 issue 表单，proposal 复用任务入口 | 功能、工程与方案讨论只需同一组目标 / 完成条件，减少入口选择 | 由维护者分配四种 type 标签；等出现稳定的不同信息需求再增加表单 |
| proposal 用仓库 Markdown，issue 用于讨论 | 决策可版本化，与实现和规范相互链接 | 明确批准版本和历史，不能靠 merge 或改状态推断批准；不单建 RFC 仓库或 ADR 副本 |
| 最小标签，暂不用项目看板和双台账 | 当前任务规模不需要多套状态同步 | 真有多人排期和跨任务依赖管理需求时再引入 |
| Conventional Commits 的简化格式 | 阅读历史可直接知道改动性质，PR 与 commit 表达一致 | 不重写旧历史，不按字符数或 scope 列表制造维护成本；语法不代替内容审查 |
| 短分支 + 默认 squash | 与“一 PR 一个完整目的”一致，临时修补不污染主线历史 | 主线不保留逐条中间提交；有独立意义的改动应拆 PR，而非依赖一个大 PR 保存多个主题 |
| 单维护者 0 个平台必需批准，多维护者至少 1 个非作者批准 | 避免作者无法自批而卡死，同时保留人的决策责任 | 单人阶段没有第二人的独立审查保障；AI review 只作辅助，不能声称已有人类双人复核 |
| 建远端与工程 CI 分步启用 | 不提前安装工具，也不把未有工作流名称写成 required checks | 初期依赖人工核验；第 3 阶段工作流实跑后再启用对应平台门禁 |

没有采纳 Git Flow、长期集成分支、强制所有任务先写 RFC、固定审批等待期、全套治理元数据、自动过期机器人、merge queue 或自动发版。这里是按当前规模作出的选择，不是认定这些做法在其他项目无效。

## 指令入口的结构修正

初版把“唯一维护源”理解成所有规则都放在 AGENTS，导致入口达到 232 行、30,311 字节；这不利于按任务控制上下文。用户确认后改为精简根入口、主题文档和明确读取时机。规则内容保留，废止“贡献指南只导航”和“所有规则必须写在 AGENTS”的组织方式。

这与 [OpenAI 的精简入口及按任务使用流程实践](https://developers.openai.com/blog/skills-agents-sdk) 一致。[Claude Code 官方说明](https://code.claude.com/docs/en/memory#write-effective-instructions) 也明确：`@` 导入会连同正文加载，拆成导入文件不会减少上下文。文件系统软链接用于避免内容复制，本身不提供按需加载；本项目保留 `CLAUDE.md` 对精简 AGENTS 的薄导入及 Claude 专有补充，详细文档使用普通链接和读取条件，不接入无条件自动加载的 rules。
