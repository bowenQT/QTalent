## 1. 新增的决定

| 编号 | 议题 | 决定 |
| --- | --- | --- |
| D-62 | 评价体系入口 | 新增「评价体系」，集中查看和修订六类规则：维度与锚点、象限落位、值得关注、前段评价标准与对应表、目标角色与发展通道、标签库。HRBP 与 CEO 可以进入；其他角色在用到规则的地方看到当前版本，并可以提修订建议（3.35.8） |
| D-63 | 修订的边界 | 只修订结构化的参数和文字：锚点与定义的文字、阈值、时间窗、门槛、模板要求、对应关系。不开放公式、表达式或自定义规则，仍不建设通用规则编辑平台（PRD v1.0 9.5 的边界不变，本文把其中的「可修改定义」落成入口） |
| D-64 | 版本与状态 | 每类规则有版本号（如 `rubric-v1`、`watch-v2`）。修订先成为草稿，经确认发布后成为新版本；已发布的版本不可修改，只能被新版本替代。一类规则同一时间最多一份草稿 |
| D-65 | 发布前预览影响 | 提交确认前，系统用现有已确认证据试算新版本的影响：哪些人进出「资料不足」、象限参考位置、值得关注，按团队写人数；HRBP 能看到名单。预览不出分数排名，不显示任何人的分数变化值 |
| D-66 | 不改写历史与可比性 | 新版本只作用于生效之后的评价。已确认的分数、冻结的盘点快照、档案版本、已生成的需求卡保留当时的版本标记，不被静默重算。发布时必须声明这次修订是否「兼容」：兼容的修订（措辞澄清、补充示例）旧分继续参与取数；不兼容的修订（等级含义变化）为取数窗口内受影响的事件生成「按新版本复核」任务，复核前这些旧分不参与新版本的取数（3.35.5） |
| D-67 | 发布权限与生效点 | 会改变评价结果的四类（维度与锚点、象限落位、值得关注、前段评价标准与对应表）由 HRBP 起草，**CEO 确认发布**；目标角色与发展通道沿用 v1.3（HRBP 维护、CEO 可改，发布即生效）；标签库沿用 v1.2。发布时选择生效点：「立即对新的评价生效」或「从下一个盘点批次开始」。盘点批次进行中，该批次所用的版本锁定，不能切换 |
| D-68 | 岗位族锚点 | 心性维度（内生动力、智慧力、坚毅力、领导力、开放性）全公司一套锚点；**专业度按岗位族（商业、设计、工程）各有一套锚点**。各族的 1–5 等级含义一致（相对当前职级预期），所以不同岗位族的人仍放在同一个能力象限里。不允许按单个团队定制锚点。答复 v1.5 第 9 节「专业度的子项」：「工程」下的问题拆解、技术方案、代码实现、工程规范、质量保障、协作交付作为工程族的**观察主题**，帮助记录与检索，不单独出分 |
| D-69 | 团队与组织 | 本期不单独建立团队或组织的评价模型。团队与组织视图由个人维度汇总（各档人数、资料不足人数，不出团队分），再加上目标角色模板描述「这个组织需要什么角色」。组织能力模型留到正式开发阶段再定 |
| D-70 | 修订来源与闭环 | 草稿可以从四处开始：判断复盘里已确认归因生成的「修订评价标准」动作、校准会上改位置写的理由、部门负责人或导师 / 助教的修订建议、HRBP 直接新建。草稿记录修订理由和依据（关联具体案例）。发布后，下一批判断复盘按版本分组对比修订是否有效（v1.3 3.16.6 不变） |
| D-71 | 原型范围 | 维度与锚点、值得关注两类做到完整可交互（起草、预览影响、提交确认、CEO 确认发布、版本对比）；其余四类只读，显示当前版本、生效时间和版本历史 |

## 2. 输入来源与理解

### 2.1 要解决的问题

> 当前产品是不是缺少了对规则和评价体系的管理入口？不然组织和 HR 对人、团队、组织的评价和建模不都是一成不变的吗？

### 2.2 现状核对（v1.5 原型与需求）

| 事实 | 说明 |
| --- | --- |
| 规则都有版本 | 维度与锚点 `rubric-v1`、象限落位（v1.2 3.8.2）、值得关注 `watch-v2`、目标角色模板 v1 / v2、前段评价标准 `xe-select-v2`、判断复盘对应表都带版本；历史分数保留当时的版本，不静默重算 |
| 只有标签库有维护入口 | 维度锚点、落位阈值、值得关注规则写死在演示数据里；目标角色模板有版本但没有编辑入口；对应表与前段评价标准在判断复盘里只能查看 |
| 修正闭环断在一半 | 判断复盘能发现「内驱力入营阶段普遍偏高」，归因后生成「修订入营选拔标准（xe-select-v3）」的改进动作，但这只是一条待办，修订本身发生在系统之外 |
| PRD 的边界 | PRD v1.0 9.5：「一期使用小规模预置词表和可修改定义，不建设通用规则编辑平台。保留规则版本；规则变化后的重新分析产生新结果，不覆盖旧盘点当时的判断」 |

### 2.3 结论

| 问题 | 结论 | 对应 |
| --- | --- | --- |
| 没有地方查看当前用的是哪版规则 | 新增「评价体系」，六类规则一处查看，用到规则的地方显示版本并能跳过去 | D-62、3.35.1 |
| 规则改不了，评价模型一成不变 | 可以修订，但只改结构化参数和文字，走起草、预览、确认、生效 | D-63～D-67 |
| 判断复盘发现问题后，修订在系统外完成 | 改进动作直接打开对应规则的草稿，发布后下一批复盘按版本验证 | D-70、3.35.7 |
| 规则一改，前后就不能比较 | 不改写历史；发布时声明是否兼容；不兼容的修订生成复核任务；盘点进行中锁定版本 | D-66、D-67、3.35.5 |
| 专业度太笼统，不同岗位的「专业」不是一回事 | 专业度按岗位族分锚点，等级含义统一 | D-68、3.36 |
| 团队和组织的评价与建模 | 先由个人维度汇总和目标角色模板表达，不单独建模 | D-69、3.37 |

## 3. 对 v1.5 的变更与新增规则

### 3.35 评价体系（新增）

#### 3.35.1 入口与页面结构

| 项 | 规则 |
| --- | --- |
| 入口 | HRBP 与 CEO 的左侧导航「评价体系」；记录页的锚点面板、速览和档案里的规则版本、判断复盘的改进动作、校准会都可以跳到对应规则 |
| 总览 | 六类规则各一张卡：名称、当前版本、生效时间与生效点、一句话说明「它决定什么」；有草稿或待确认时写明状态和起草人；有来自判断复盘的修订信号时写一行，如「内驱力入营阶段 8 人中 6 人前段偏高，已归因为评价标准」 |
| 规则详情 | 当前版本的内容（按类别呈现，见 3.35.2）、版本历史（每版的发布人、确认人、生效点、修订理由与依据）、任意两版对比 |
| 草稿 | 在当前版本上直接修改；被改动的地方标出原值；修订理由必填，可以关联判断复盘案例、校准理由或修订建议作为依据 |
| CEO 视角 | 首页「需要我看」出现「评价规则修订待你确认」；点开是草稿的对比、理由、依据和影响预览，可以确认发布或退回（退回写一句理由） |
| 依据的可见范围 | 依据按查看人的权限呈现。CEO 在确认页和版本历史里，来自判断复盘的依据只看批次、维度、偏差人数和归因类别（与 v1.4 3.22 同口径），不看被评价人名单、案例和按评价人的任何内容；校准理由与修订建议只看来源和条数。案例、人名和原文只对有权限的 HRBP 展开 |

#### 3.35.2 六类规则与可修订的内容

| 规则 | 版本前缀 | 可修订的内容 | 发布 | 原型 |
| --- | --- | --- | --- | --- |
| 维度与锚点 | `rubric-` | 维度定义；1–5 分的行为锚点（心性维度一套，专业度按岗位族各一套，3.36）；挂在维度下的观察主题 | HRBP 起草，CEO 确认 | 可交互 |
| 象限落位 | `place-`（原属 `rubric-v1`，本版拆出单独版本） | 取数窗口、高低分界、落位门槛、加分项条件（v1.2 3.8.2 各项） | HRBP 起草，CEO 确认 | 只读 |
| 值得关注 | `watch-` | 各条入选规则的阈值与时间窗、提名来源（v1.4 3.20、v1.5 3.31）；不能新增按分数挑人的规则 | HRBP 起草，CEO 确认 | 可交互 |
| 前段评价标准与对应表 | `xe-select-`、`hire-`、对应表各自版本 | 面试与入营选拔的维度、等级定义、题目要点；前后阶段的维度与等级对应关系（v1.3 3.16） | HRBP 起草，CEO 确认 | 只读 |
| 目标角色与发展通道 | 每个模板各自版本 | 模板的职责、必须与加分要求、可替代的放宽表述；通道清单 | HRBP 维护，CEO 可改，发布即生效（v1.3 3.15） | 只读 |
| 标签库 | 沿用 v1.2 | 收录、并入、停用标签 | 沿用 v1.2 | 已有页面，从总览进入 |

象限落位从 `rubric-v1` 中拆出单独版本，是因为调阈值不该和改锚点文字混在一次发布里；拆分后 `rubric-v1` 的锚点内容不变，原有分数的版本标记不变，演示数据中的落位规则记为 `place-v1`。

#### 3.35.3 修订流程与状态

| 状态 | 谁 | 能做什么 |
| --- | --- | --- |
| 草稿 | HRBP | 修改、写理由、关联依据、预览影响、删除草稿 |
| 待确认 | CEO | 查看对比、理由、依据和影响预览；确认发布，或写理由退回；HRBP 可以撤回到草稿 |
| 已排期 | — | 确认发布、生效点选「下一个盘点批次」时进入；到点自动生效；生效前 HRBP 可以撤回到草稿，需要 CEO 再次确认 |
| 生效中 | — | 新的评价按这一版；页面与评价记录上显示版本号 |
| 已替代 | — | 被新版本替代后只读，仍能查看和对比 |

- 确认发布用朱印压印反馈，写确认人与时间；确认发布 5 秒内可以撤销。
- 目标角色模板和标签库不经过「待确认」，沿用原规则。

#### 3.35.4 影响预览

| 规则类型 | 预览内容 |
| --- | --- |
| 阈值、时间窗、门槛（象限落位、值得关注） | 用现有已确认证据按新旧两版各算一次：进入 / 离开「资料不足」、参考位置变化、进入 / 离开值得关注的人数，按团队列出；HRBP 可以展开名单，CEO 看人数和团队分布 |
| 锚点与定义的文字（维度与锚点、前段评价标准） | 文字修订不会自动改变已有分数。预览写：取数窗口内用到这个维度（或这个岗位族锚点）的事件数、评分人数；声明为不兼容时，将生成多少条复核任务、分给哪些评分人 |
| 对应表 | 下一次判断复盘里受影响的对照单元数 |

- 预览只在发布前提供，结果随草稿保存，确认人看到的是同一份。
- 预览不出现分数排名、个人分数变化值或「谁会变好 / 变差」的措辞；资料不足不写成反向证据。

#### 3.35.5 不改写历史与可比性

| 情形 | 规则 |
| --- | --- |
| 已有的分数、快照、档案版本、需求卡 | 保留当时的版本标记，不静默重算（沿用 v1.2 3.7.4 第 5 条、PRD 9.5） |
| 兼容的修订 | 措辞澄清、补充示例、调整观察主题；旧分继续参与取数，卡片上照常显示原版本号 |
| 不兼容的修订 | 等级含义变化，或岗位族锚点首次启用；为取数窗口内受影响的事件生成「按新版本复核」任务：AI 按新锚点给建议分，原评分人确认，原评分人不在时由 HRBP 确认。原分保留并显示原版本；复核确认后的分按新版本参与取数。复核完成前，这些旧分不参与新版本的取数，不满足落位门槛的人进「资料不足」区，不当作反向证据 |
| 阈值类修订 | 不涉及复核；生效后按新阈值计算，生效前的冻结快照不变 |
| 判断复盘 | 按版本分组对比；跨版本的对照仍用人工确认的对应表（v1.3 D-36） |

#### 3.35.6 生效点与盘点锁定

- 发布时二选一：「立即对新的评价生效」或「从下一个盘点批次开始」。
- 盘点批次从发起到确认冻结期间，这次盘点用到的规则（维度与锚点、象限落位）版本锁定；这期间发布的这两类新版本只能选「从下一个盘点批次开始」。值得关注、前段评价标准与对应表不参与盘点取数，不受锁定。
- 生效时间之前保存的事件，即使之后才确认分数，也按保存时生效的版本（避免同一件事前后两个口径）。

#### 3.35.7 与判断复盘、行动与复盘的衔接

- 判断复盘里已确认归因为「评价标准」的改进动作，按钮从「生成行动」改为「起草修订」：打开对应规则的草稿，自动带上这次复盘的批次、维度、案例和归因理由作为依据。
- 草稿发布后，对应的改进动作在「行动与复盘」里记为已执行，观察目标是「下一批判断复盘里该维度的偏差人数变化」；样本不足时只提示，不下「改进有效」的结论（v1.3 3.16.6 不变）。
- 校准会上把人拖离参考位置时写的理由，HRBP 可以在落位规则的草稿里引用为依据。

#### 3.35.8 修订建议

- 部门负责人、导师 / 助教在记录页的锚点面板、档案的维度说明里可以点「提修订建议」：选是哪条锚点或定义、写一句理由，可以引用一件事作为例子。
- 建议进入 HRBP 待办「规则修订建议」，HRBP 可以纳入草稿、合并或不采纳（写理由）；提建议的人能看到处理结果。
- 修订建议不改变任何人的分数，也不会自动形成草稿。

### 3.36 岗位族与专业度锚点（修订 v1.2 3.7.2）

| 项 | 规则 |
| --- | --- |
| 岗位族 | 商业、设计、工程三族（建议默认，来自人才发展大图的专业能力划分）；每人归属一族，来源是组织表里的岗位，由 HRBP 维护；归属变化记录时间 |
| 锚点结构 | 专业度在每个岗位族下各有一套 1–5 分锚点；等级含义统一：1 明显低于当前职级预期，3 达到当前职级预期，5 可以承担更高一级职责；各族只在行为示例上不同 |
| 打分 | 记录事件时，专业度按被记录人在事件日期所属的岗位族锚点打分；AI 建议分引用该族的锚点；锚点面板显示岗位族和版本 |
| 观察主题 | 工程族下设问题拆解、技术方案、代码实现、工程规范、质量保障、协作交付六个观察主题，商业族、设计族的主题尚待确认（第 9 节）；观察主题用于整理、检索和找人，不单独出分，不进象限 |
| 象限 | 专业度轴仍是一条；不同岗位族的人放在同一个象限里，参考位置和落位门槛不变 |
| 版本 | 岗位族锚点首次启用属于不兼容修订（3.35.5），演示中为 `rubric-v2` 的草稿 |

### 3.37 团队与组织视图的边界

| 项 | 规则 |
| --- | --- |

## 6. 新增与修订的验收用例

| 编号 | 场景 | 通过标准 |

| AC-75 | 起草与边界 | 草稿只能改结构化参数和文字，被改动处标原值；理由必填；没有公式或自定义规则入口；值得关注不能新增按分数挑人的规则 |
| AC-76 | 影响预览 | 阈值类修订显示进出资料不足、参考位置、值得关注的人数并按团队列出；HRBP 能展开名单，CEO 只看人数与团队分布；没有分数排名和个人分数变化值 |
| AC-77 | 确认发布 | 会改变评价结果的四类须 CEO 确认；退回必须写理由；确认 5 秒内可撤销。选「立即对新的评价生效」的，确认后旧版本变为「已替代」；选「从下一个盘点批次开始」的，新版本为「已排期」，旧版本继续生效到新版本实际生效时才变为「已替代」，排期中撤回后旧版本继续有效；已替代的版本可查看、可对比 |
| AC-78 | 不改写历史 | 发布新版本后，已确认分数、冻结快照、档案版本、需求卡的版本标记不变；不兼容修订生成复核任务，复核前这些旧分不参与新版本取数；排除它们之后重新检查落位门槛，仍满足的照常落位（例如只修订领导力、开放性这类加分项维度），不满足的进资料不足而不是低档 |
| AC-79 | 生效点与锁定 | 盘点批次进行中，维度与锚点、象限落位的修订只能选「从下一个盘点批次开始」，值得关注等不参与盘点取数的规则不受限制；生效前保存的事件按保存时的版本 |
| AC-80 | 判断复盘闭环 | 归因为评价标准的改进动作可以一键起草修订，草稿带上批次、维度、案例和理由；CEO 在确认页和版本历史里只看到批次、维度、偏差人数和归因类别，看不到案例和被评价人；发布后行动记为已执行，下一批复盘按版本分组 |

## 10. 风险提示

- **借修订「调」出想要的名单。**阈值类修订可以预览名单，存在为了让某人进出值得关注而改规则的可能。修订理由必填并关联依据，版本历史与预览结果随版本永久保存，发布须 CEO 确认，预览名单只对 HRBP 可见。
- **改得太频繁，前后不可比。**盘点进行中锁定版本；不兼容修订必须复核才进入取数；判断复盘按版本分组，修订效果要等下一批验证，样本不足不下结论。
- **复核负担过重。**一次不兼容修订可能产生大量复核任务。预览先写出任务数和评分人分布，量大时先在一个岗位族或一个维度上发布。
- **岗位族之间口径漂移。**各族锚点只在行为示例上不同，等级含义统一；校准会按族查看分布，发现某族整体偏高或偏低时，归因为评价标准再修订，不在象限上做换算。
- **做成通用规则平台。**只开放结构化参数与文字，不开放表达式；新增规则类型须另出需求。
