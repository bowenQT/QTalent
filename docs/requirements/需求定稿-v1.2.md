## 2. 产品体验原则（设计系统与原型共同遵守）

1. **意图优先。**用户先用一句话、语音或一段材料说明要做什么，系统围绕这个任务生成活文档，而不是让用户先在导航里找页面、填表。
2. **来源即视觉语言。**原始事实、本人自述、管理观察、AI 推断、人工结论分别用不同的视觉材质表示：
   - AI 生成的内容（含 AI 建议分）有淡淡的流光底，表示"建议中"；
   - 人编辑或确认后"落墨"，变成实色正文，并带上确认人；
   - 引用以角标呈现，悬停时展开原文片段，点击可跳到文档段落或录音时间点。
3. **过程可见，但不打扰。**AI 的步骤（读取需求 → 检索授权范围内的 38 人 → Jev 核对 4 项要求）显示为一行可折叠的进度轨迹；流式结果逐块长出来，没有转圈等待。
4. **直接操作优先于对话。**能点、拖、改的地方不要求用户输入一段话；对话只用于发起任务和追问。
5. **分数必须有出处。**每个分数都能看到：依据哪条行为锚点、引用了哪段原文、谁打的、是 AI 建议还是人工确认、用的哪版评分规则。没有足够证据的维度显示"资料不足"，不出分；不出现综合总分和排名（见第 3.10 节）。
6. **人的责任清晰可见。**草稿和正式版本在视觉上明确区分；确认是一个有分量的动作（冻结快照），撤销随处可用。

## 3. 对 PRD v1.0 的变更

### 3.1 FR-04 / 第 11 节：移动端录音（扩大范围）

v1.0 写的是"长会议优先上传已录好的文件，手机长时间录制与实时转写不进一期"。现改为对标「得到」：

| 环节 | 要求 |
| --- | --- |
| 模式选择 | 底部弹出的录音面板，选择「观察速记」「多人会议」「上传录音文件」；显示单次时长上限（具体数值以联调为准）；语言选择 |
| 录制中 | 实时转写逐句出现，未定稿的字用浅色显示；底部工具：**打标记**（标记关键片段）、**随手记**（插入文字备注）、**@某人**（在当前时间点关联人员，替代得到的"拍重点"）；暂停 / 完成；可最小化为悬浮条后继续浏览其他页面 |
| 完成后 | 进入异步处理状态，由 IP 形象提示"转写与整理中，可以直接返回"；任务在工作台持续可见 |
| 结果：人才纪要 | 对应得到的"图文纪要"：会议摘要、涉及人员、新增关键事件卡（背景—行为—结果—来源时间点，含 AI 建议分）、**待核对**（如"小王"指谁）；另一个标签页是带说话人与时间点的文字记录；顶部可播放原录音，点击事件跳到对应时间点 |
| 追问 | 底部输入框支持"按住说话 / 轻点输入"，并提供推荐追问（如"谁在这次会议里展现了推动力？""有要跟进的事吗？"） |

开发期约束（不影响原型）：
- 实时转写接通义听悟的实时接口，离线长音频继续走 v1.0 的异步链路；
- 浏览器在锁屏或切到后台时会暂停页面和麦克风（iOS Safari 尤其明显），这是 Web 平台本身的限制，与是否在企业微信内无关。界面要提示保持亮屏，并尽量调用屏幕常亮接口；录音分段上传落盘，中断后可以续录，已上传的分段不丢失；
- 具体时长上限、格式和并发在联调后确定，并展示在面板上。

### 3.2 新增：Landing 批次与对人复盘（承接 CEO 场景）

依据 S3：Landing 面向所有七牛新人，为期 4 周进组做项目，每周对事复盘、每两周对人复盘，结营时评估，形成"第一份判断力档案"。

- 不新建独立子系统，作为**重点跟踪的一个批次模板**实现：一个批次 = 期次 + 新人名单 + 议题（议题即项目，见 3.6）+ 导师/助教 + 复盘节奏。
- 双周对人复盘是一份活文档：自动带入两周内的关键事件、录音证据和导师评价，**按能力象限的维度组织**；CEO 关注的"判断力、推动力"作为观察主题挂在相应维度下（建议默认：判断力 → 智慧力，推动力 → 内生动力、领导力），不改动维度原名。导师和 HRBP 补充、确认分数后，复盘确认。
- 结营时，每位新人的复盘汇总进人员档案，作为"第一份档案"，并完成第一次象限校准（见 3.8）；后续项目找 owner 和盘点都可以引用。
- 现有 Landing 档案（S5）里按日期排列的复盘节点（周终 Roleplay、导师团复盘、Milestone 述职/分享、终期 Milestone），每个节点的"评价人 + 评价内容"对应系统里的一条或多条关键事件，演示数据按这个结构构造。

### 3.3 FR-15 / 第 11.4 节：入口改为纯 H5

- 取消企业微信作为主入口：手机端以 iOS Safari、Android Chrome 为目标浏览器，桌面以 Chrome / Safari / Edge 为目标浏览器。
- 登录沿用预置独立账号（v1.0 本就不依赖企业微信 SSO）。
- 麦克风访问要求 HTTPS 部署；首次录音需要处理浏览器的授权弹窗，权限被拒时退回文字输入和文件上传（沿用 FR-15）。
- 可以加入"添加到主屏幕"（PWA），提供接近 App 的入口；不作为必做项。
- 相应验收调整：AC-08、AC-26 中的"企业微信"改为"手机浏览器"；PRD O-06 关闭。

### 3.5 用户、角色与权限（替换 PRD 第 4.1 节与第 12.1 节矩阵）

#### 3.5.1 五类业务用户

| 角色 | 典型身份 | 核心任务 | 最关键结果 |
| --- | --- | --- | --- |
| CEO | 公司负责人 | 一句话发起重要项目找 owner；看关键人才与象限分布；确认重大用人方案 | 快速得到有依据的人选与方案 |
| HRBP | 按人员归属分工的 HRBP | 录入关键事件、校准分数、组织盘点与象限校准、准备调整方案、跟踪重点人员 | 资料齐备、口径一致、行动可追踪 |
| 部门负责人 | 在职人员表中"是否部门负责人"为是 | 记录本部门人员和所负责项目成员的关键事件；建项目、找人；参与本部门盘点校准 | 明确可用人选，团队判断有据 |
| 导师 / 助教 | XEngineer 训练营、Landing 等批次的导师和助教 | 给所带学员录入评价（关键事件 + 打分），参加导师团复盘 | 低成本完成评价，看到学员的完整成长记录 |
| 员工 | 全体员工，含新人 | 补充本人经历与自述、表达意愿、纠错、查看发布给本人的反馈与行动 | 了解自己的资料与下一步 |

技术管理员保留为维护角色：配置账号、组织目录和服务参数，不因此获得业务数据权限。

一个人可以同时具有多种身份（如部门负责人同时担任 Landing 导师），权限取各身份范围的并集，但每次访问仍按"角色动作 + 授权范围 + 内容可见性"逐项判断。

#### 3.5.2 范围怎么确定

| 角色 | 范围来源 |
| --- | --- |
| CEO | 全公司 |
| HRBP | 在职人员表 HRBP1 / HRBP2 指向本人的人员；演示可配置一个全公司账号 |
| 部门负责人 | 本人负责的组织及其下级组织的人员；外加本人担任 owner 的项目成员（只限项目相关资料，见 3.6.3） |
| 导师 / 助教 | 批次配置中本人所带的批次 / 议题的学员 |
| 员工 | 本人 |

组织架构不自动等同于授权范围；以上是默认规则，真实上线前由 HR 确认。

### 3.6 项目（新增对象，FR-09 的承载方式随之调整）

#### 3.6.1 定义

项目是一等对象，人与项目多对多：一个人可以在多个项目里，一个项目有多名成员。

| 字段 | 说明 |
| --- | --- |
| 基本信息 | 名称、类型（业务项目 / Landing 议题 / 训练营课题 / 黑客松 / 专项）、目标、所属组织、起止时间 |
| 状态 | 筹备中 / 进行中 / 已结束 / 已归档 |
| owner | 项目负责人，可以为空（正在找 owner） |
| 成员关系 | 人员、项目内角色、投入方式（全职 / 兼职 / 顾问）、加入与退出时间、贡献说明；成员变化保留历史 |
| 用人需求 | 找 owner / 找人的需求卡，有版本；确认后候选人成为成员（见 3.6.2） |
| 关联事件 | 发生在这个项目里的关键事件 |

#### 3.6.2 与找 owner 的关系

- 「找 owner / 项目找人」是在项目里发起的一次用人需求。CEO 一句话描述一个重要项目时，系统先创建（或匹配已有）项目，再生成需求卡。
- 需求卡 → 候选人 → 对比 → 项目用人方案的流程沿用 v1.0 FR-09 与 v1.1 原型模块 C；方案确认后，选定人员写入项目成员关系，owner 字段随之更新。
- 候选人比较除了 v1.0 的"支持 / 不支持 / 资料不足 / 证据冲突"外，可以展示候选人在相关维度上的已确认分数及证据，但**不按分数排序**，不出现总分（见 3.10）。

#### 3.6.3 增删改查规则

| 操作 | 规则 |
| --- | --- |
| 新建 | CEO、HRBP、部门负责人可以新建；导师可以在所带批次下新建议题项目 |
| 查看 | 项目基本信息和成员对项目成员与范围内的管理者可见；用人需求、候选人名单属于管理受限资料，只对发起人、CEO 和相关 HRBP 可见 |
| 编辑 | 创建者、项目 owner、CEO，以及项目所属组织在其范围内的 HRBP / 部门负责人 |
| 删除 | 没有关联事件和方案时可以删除（5 秒撤销）；已有关联时只能**归档**，因为事件和已确认方案的快照引用了它 |
| 成员调整 | 加入、退出、改角色都记录时间与操作人，供任用后复盘使用 |

项目 owner 若本身不是部门负责人，只获得编辑本项目信息与成员的权限，不因此获得成员的管理资料权限。

### 3.7 关键事件与量化打分（修订 PRD 第 7、9 节与 FR-05～FR-07）

#### 3.7.1 关键事件

- v1.0 的"证据 / 观察记录"统一改称**关键事件**，最小结构沿用 PRD 第 7.2 节（谁、何时、什么情境、做了什么、结果、来源、信息性质、谁能看、有什么不确定），新增"所属项目"和"维度分"。
- 来源：一句话记录、录音纪要、导师评价、材料上传解析、历史资料导入（3.9）。
- 一次多人参与的复盘会可以产生多条事件；同一事件在多份材料中出现时合并为一条并关联多个来源，不重复计数（沿用 PRD 7.3 第 3 条）。

#### 3.7.2 评分维度（规则版本 rubric-v1）

依据附件「人员能力象限」（S8）：

| 轴 | 维度 | 类型 | 说明 |
| --- | --- | --- | --- |
| 专业度 | 专业度 | 核心 | 对标当前岗位序列与职级（N3–N7）的预期；商业 / 设计 / 工程作为专业方向标签，不另拆维度 |
| 潜力 | 内生动力 Motivation | 核心 | 主动发现问题、主动补位与闭环、带着假设求助、追求问题解决而非任务完成 |
| 潜力 | 智慧力 Wisdom | 核心 | 结构化拆解、结论→依据→取舍、系统性收敛、识别关键矛盾、设计最小验证路径 |
| 潜力 | 坚毅力 Grit | 核心 | 受挫后复盘再投入、长期攻坚保持输出、主动认领失误、压力下维持交付标准 |
| 潜力 | 领导力 Leadership | 加分 | 推动共识、主动组织对齐、理性协调冲突、带动同伴、为集体目标负责 |
| 潜力 | 开放性 Openness | 加分 | 倾听质疑、反馈后改进、走出舒适区、借鉴他人做法、新信息下调整判断 |

附件中每个维度的"具体行为示例"作为观察提示和锚点素材，不是打分清单。

#### 3.7.3 1–5 分锚点（通用模板，各维度的具体锚点待 HR 确认）

| 分 | 含义（潜力维度） | 含义（专业度） |
| --- | --- | --- |
| 1 | 在本事件中出现与该维度相反的明确行为 | 明显低于当前职级预期 |
| 2 | 相关行为偶发，需要他人推动才发生 | 部分达到当前职级预期 |
| 3 | 在常规情境下稳定表现出该维度的行为 | 达到当前职级预期 |
| 4 | 在有难度或模糊的情境下主动表现，并有可见结果 | 超出当前职级预期 |
| 5 | 在高难情境下表现突出，并带动他人或形成可复用的方法 | 可以承担更高一级职责 |

- 分数评价的是**这一次事件中的行为**，不是稳定人格结论；单次低分不能推断"低潜力"（沿用 PRD 9.4）。
- 事件没有涉及的维度记为"未体现"；涉及但信息不够（只有参与、没有具体行为或结果）的维度记为"资料不足"。两者都不出分，也都不等于低分。
- 团队结果不复制给每位成员；只对个人的行为和贡献打分（沿用 PRD 7.3 第 4 条）。

#### 3.7.4 打分流程

1. **AI 建议分。**事件保存后，AI 判断涉及哪些维度，对信息足够的维度给出建议分；每个建议分必须引用一条锚点和事件原文片段，并标明模型与规则版本。AI 不得依据语气、学校、学历、年龄、性别等打分。
2. **录入人确认。**录入人逐项确认或改分；改分时可写一句理由（不强制）。确认后分数"落墨"并署名，计入人员档案。未确认的 AI 建议分不参与象限。
3. **HRBP 校准。**HRBP 可以在归属范围内调整已确认的分数，必须写理由；原分、原评分人、调整人和理由都保留，界面显示最终分并可展开修订历史。
4. **多人评价与冲突。**一次复盘会可以有多位评价人对同一学员各自打分；同一维度分差 ≥ 2 时标记为"证据冲突"，进入 HRBP 校准队列。
5. **规则变更。**锚点或维度调整产生新的规则版本；旧分数保留原版本标记，不被静默重算（沿用 PRD 9.5）。

### 3.8 能力象限（新增）

#### 3.8.1 形态

```
潜力 ↑
 ┌──────────┬──────────┐
 │ 高潜待练 │ 双高     │
 ├──────────┼──────────┤
 │ 待观察   │ 专业骨干 │
 └──────────┴──────────┘
              专业度 →
资料不足：单独列在象限外，并说明缺哪类证据
```

象限名称是建议默认，可在设计阶段调整，但不得使用"淘汰""低绩效"等定性词。

#### 3.8.2 参考位置的计算（建议默认，属于规则版本的一部分）

| 项 | 规则 |
| --- | --- |
| 取数范围 | 近 12 个月内、已确认（含已校准）的关键事件维度分 |
| 专业度参考值 | 专业度分的均值 |
| 潜力参考值 | 内生动力、智慧力、坚毅力三项各自取均值后再取均值 |
| 加分项 | 领导力或开放性均值 ≥ 4 时在头像上显示加分标记，供校准时参考；不参与均值，不会拉低潜力 |
| 高 / 低分界 | 参考值 ≥ 3.5 为高 |
| 落位门槛 | 每条轴至少有 2 条来自不同事件的已确认分数，潜力轴三项核心至少两项有分；不满足的人进"资料不足"区 |

#### 3.8.3 校准与冻结

- 系统给出的是**参考位置**（以虚影表示）。正式位置在盘点批次或 Landing 结营复盘中由 HRBP 发起，部门负责人参与，HRBP 或 CEO 确认。
- 校准时可以把人拖到与参考位置不同的象限，必须写一句理由；确认后冻结为快照（含当时的维度分、证据和规则版本）。
- 冻结后出现新的已确认事件，若参考位置变到另一个象限，只在人员和盘点视图上提示"可能需要重新校准"，不自动移动正式位置。
- 人员档案中显示当前正式位置、最近一次校准时间，以及历次校准的位置轨迹。

#### 3.8.4 展示约束

- 象限图上只显示头像与化名，不显示精确的轴数值；点开某人可以看维度分、事件数量和证据。
- 同一象限内按团队或姓名排列，不按分数排序；任何人员列表都不提供按分数排序。
- 员工、导师 / 助教看不到任何象限信息；这条要在档案、搜索、项目、AI 问答、导出等所有入口生效（员工问"我在哪个象限"，回答为不可见）。

### 3.9 历史资料导入（修订 FR-01、FR-03）

#### 3.9.1 人员基础字段白名单（来源：在职人员信息表，S6）

| 导入 | 字段 |

#### 3.9.2 历史分数作为证据（不换算）

| 实训营评审（作品分、个人分、能力等级 S/A/B、亮点、不足、导师评价） | 同上，类型为"训练营评审" |

### 4.3 交互巧思清单（原型需实现）

- **落墨**：AI 草稿被人确认时，流光底收拢成实色正文，并在页边落下确认人的小签名。
- **分数落墨**：AI 建议分是带流光的空心点阵；确认时实心化并署名；改分时原 AI 分留下淡影，显示差值。
- **引用角标**：悬停展开原文片段；录音来源可以就地播放那 10 秒。
- **证据飞入**：核对归属后，事件卡沿弧线飞向对应人员头像，计数随之 +1。
- **需求即时重排**：修改需求卡中的一项要求，候选人列表做位置过渡动画重排，变化的证据高亮。
- **拖入槽位**：把候选人拖进方案的角色槽位，槽位吸附并显示该角色对应的证据缺口。
- **象限校准**：拖动人员头像时，AI 参考位置留下虚影和一条连线；松手到不同象限时弹出一句话理由输入；全部确认后整张象限做一次"压印"。
- **冻结快照**：确认版本时，文档做一次"压印"动效，生成版本号；之后的修改自动进入新草稿。
- **差异视图**：新证据进入或方案改版时，用行内差异标出新增和变化。
- **撤销 Toast**：直接保存的记录、删除的项目在底部显示 5 秒倒计时撤销。
- **IP 形象状态**：倾听、检索、思考、完成、需要你确认、出错，各有对应的微动画，出现在输入框、处理状态和空状态处。

## 6. 设计系统交付清单

- **Tokens**：颜色（中性色阶、智能强调色、来源材质、状态色、象限四色与"资料不足"色）、字体与字号阶梯（中文优先）、间距、圆角、阴影/层级、动效曲线与时长。
- **来源材质规范**：事实 / 自述 / 观察 / AI 推断 / 人工结论的视觉区分；判断状态（支持 / 不支持 / 资料不足 / 冲突）；分数状态（AI 建议 / 已确认 / 已校准 / 资料不足 / 未体现）。
- **组件**：输入框（文字 / 语音 / 附件 / 斜杠命令）、Agent 进度轨迹、活文档块、关键事件卡、**维度分组件（1–5 点阵、锚点浮层、修订历史）**、**象限图（参考虚影、拖动校准、资料不足区）**、**项目卡与成员关系列表**、引用角标与原文浮层、人员行与人员卡、候选卡、方案角色槽位、版本条与差异视图、待核对卡、校准队列卡、状态徽标、撤销 Toast、录音面板与悬浮录音条、音频播放器、空状态 / 加载 / 失败 / 无权限。
- **IP 形象**：2–3 个概念候选供选择，选定后输出 6 种状态的动画规范；原型阶段允许使用矢量占位。

## 8. 风险提示

- **工作量**：一人 + AI 在原型之后的剩余时间内完成 v1.0 全部验收用例与本版新增用例，风险很高，建议原型定稿时一并决定开发裁剪。
- **录音扩范围**：实时转写和浏览器锁屏/后台中断录音，是最大的技术不确定项，应在开发首日优先联调。
- **打分被当成定论**：有了分数和象限后，使用者容易跳过证据直接看位置。界面上分数必须和证据、评分人、资料不足一起出现，象限位置必须经过人工校准才算正式。
- **AI 打分的一致性**：同一段材料多次生成的建议分可能不同。开发阶段需要用一组固定样例检查稳定性；原型中的建议分是预置的。
- **演示真实性**：原型的 AI 结果是脚本化的。比赛时如仍有预置结果，需要按 PRD 第 15.3 节如实标注。
